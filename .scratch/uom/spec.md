# UOM: Get, Create, Update

## Problem Statement

Разработчик решения может работать с Product через SDK, но пока не может получать,
создавать и изменять UOM тем же способом. Нужен небольшой следующий справочник,
на котором можно проследить разработку модели, запросов, методов и тестов.

Product — утверждённый образец. Этот срез расширяет SDK новой сущностью,
сохраняя существующую архитектуру и контракты общих типов.

## Solution

Добавить пакет `uom` в группу `entity`: модель чтения `UOM`, обёртку `Service`,
конструктор `NewService`, отдельные `CreateRequest` и `UpdateRequest`.
Предоставить Get/Create/Update по образцу Product; остальные возможности оставить TODO.

## User Stories

1. Как разработчик решения, я хочу получить UOM по ID, чтобы прочитать её данные.
2. Как разработчик решения, я хочу читать предустановленные и пользовательские UOM одним типом, чтобы использовать общий интерфейс.
3. Как разработчик решения, я хочу сохранить строковый code, включая ведущие нули и буквы, чтобы не исказить код UOM.
4. Как разработчик решения, я хочу читать owner и group как ссылки, чтобы использовать уже существующие общие типы.
5. Как разработчик решения, я хочу создать UOM, указав только name, чтобы остальные значения определил сервер.
6. Как разработчик решения, я хочу передать необязательные поля при создании, чтобы сразу задать данные пользовательской UOM.
7. Как разработчик решения, я хочу обновить отдельные поля UOM, чтобы не отправлять остальные данные повторно.
8. Как разработчик решения, я хочу различать отсутствие поля, null и явное значение, чтобы точно выразить тело запроса.
9. Как разработчик решения, я хочу передать shared=false и пустую строку без их потери, чтобы явно изменить значение.
10. Как разработчик решения, я хочу получить ошибку сервера при попытке изменить предустановленную UOM, чтобы понимать ограничение API.
11. Как разработчик решения, я хочу получать созданную или изменённую UOM из ответа сервера, чтобы видеть фактическое состояние.
12. Как разработчик решения, я хочу получить локальную ошибку для неверного ID, пустого имени при создании и пустого Update, чтобы не выполнять заведомо неверный запрос.
13. Как разработчик решения, я хочу распознавать APIError и исходные ошибки через errors.As/errors.Is, чтобы обрабатывать их программно.
14. Как разработчик решения, я хочу управлять отменой через context, чтобы не продолжать ненужный запрос.
15. Как разработчик решения, я хочу получать ошибку неожиданного или некорректного ответа, чтобы не использовать недостоверный результат.
16. Как разработчик решения, я хочу видеть точные границы поддержки UOM в документации SDK, чтобы не считать весь API реализованным.
17. Как изучающий Go разработчик, я хочу видеть небольшие изменения и их проверки по отдельности, чтобы понимать процесс разработки.

## Implementation Decisions

### Публичный интерфейс и маршруты

- Модель данных — `uom.UOM`, обёртка — `uom.Service`, конструктор — `uom.NewService`.
- Конструктор принимает существующий `*transport.Client`, возвращает обёртку и ошибку; nil client отклоняется.
- Get принимает context и ID; Create — context и CreateRequest; Update — context, ID и UpdateRequest.
- Все три метода возвращают `(*UOM, error)`.

| Метод SDK | Метод HTTP | Маршрут относительно API 1.2 |
| --- | --- | --- |
| Get | GET | `entity/uom/{id}` |
| Create | POST | `entity/uom` |
| Update | PUT | `entity/uom/{id}` |

### Модель чтения

| JSON-поле | Поле Go | Тип |
| --- | --- | --- |
| meta | Meta | model.Meta |
| id | ID | string |
| accountId | AccountID | string |
| updated | Updated | model.DateTime |
| name | Name | string |
| description | Description | string |
| code | Code | string |
| externalCode | ExternalCode | string |
| owner | Owner | *model.Reference |
| group | Group | *model.Reference |
| shared | Shared | bool |

- Использовать существующие Meta, DateTime и Reference, без новых общих типов и expand.
- Незаполненные ссылки и Updated оформляются по образцу Product.
- В документации есть противоречие: таблица атрибутов помечает accountId как
  «Обязательное при ответе», но в официальных примерах списка у предустановленных UOM
  «дюйм» (code=039) и «мес» (code=362) этого поля нет. Для предустановленных UOM
  допускаем отсутствие accountId по этим примерам; не вводить проверку обязательности
  accountId на основании одной таблицы.
- У предустановленной UOM могут отсутствовать accountId, owner, group и shared.
  Отсутствующие поля читаются как нулевые значения соответствующих типов;
  Shared=false не служит признаком пользовательской или предустановленной UOM.
- Неизвестные поля ответа не мешают чтению, как в существующем транспорте.

### Модели записи

- Поддержать name, description, code, externalCode, owner, group и shared.
- В CreateRequest Name имеет тип string и обязателен; остальные поля используют `model.Field[T]`.
- В UpdateRequest все семь полей используют `model.Field[T]`.
- Строковые поля используют string, Shared — bool, Owner и Group — model.Reference внутри Field.
- Для Field использовать `omitzero`, как в Product: незаданное поле отсутствует в JSON,
  Value передаёт значение, включая false и пустую строку, Null передаёт явный null.
- Возможность закодировать null не обещает, что сервер разрешает очистку конкретного поля.
  Допустимость null и ограничений значений остаётся на стороне API, как в Product.
- Meta, ID, AccountID и Updated не включать в модели запросов.
- Update отправляет только заданные поля, не выполняет предварительный Get и локальное слияние.

### Валидация, ответы и ошибки

- Get/Update проверяют форму UUID по образцу Product, без ограничения версии UUID.
- Create отклоняет только Name==""; не добавлять trim и новые проверки строк.
- Update отклоняет request без заданных полей. Явные false, пустая строка и null считаются заданными.
- Ограничения длин, непустого имени при Update и допустимости ссылок проверяет сервер.
- Предустановленные UOM доступны для чтения; изменение разрешено только для пользовательских.
  SDK не определяет происхождение UOM локально и возвращает APIError при отказе сервера.
- Успех — HTTP 200 и непустой ID в декодированном объекте, по образцу Product.
- Возвращать данные ответа сервера. При ошибке возвращать nil вместо частично прочитанной UOM.
- Сохранить контекст операции, доступность APIError через errors.As и исходных ошибок через errors.Is;
  не дублировать префикс moysklad:.
- Использовать существующую обработку context, заголовков, gzip и ошибок транспорта.
- Не добавлять автоматические повторы, в том числе POST после неоднозначного сбоя.
- Сохранить устройство Product: сущность и её обёртка находятся в одном пакете;
  общий код выполнения запросов остаётся приватным для этого пакета.

## Testing Decisions

- Проверять публичное поведение UOM по существующим образцам тестов Product;
  не закреплять приватные вспомогательные функции и внутреннее устройство Service.
- Основная точка проверки методов — локальный HTTP-сервер с настоящим transport.Client:
  метод, маршрут, отсутствие лишних query-параметров, тело, заголовки, результат и ошибки.
- Проверить значения всех согласованных полей из неизменённой upstream-фикстуры UOM,
  включая строки, Shared=false, ссылки и Updated; одного успешного декодирования недостаточно.
- Дополнить чтение случаем предустановленной UOM без полей пользовательской UOM
  и случаем с неизвестным полем. Собственные случаи держать отдельно от upstream.
- Модель и request-модели проверить через encoding/json и encoding/json/v2,
  используя принятый в Product подход к таблице кодеков.
- Тела Create/Update сравнивать с независимо заданными golden JSON,
  а не с результатом сериализации SDK, использованным как ожидаемое значение.
- Проверить минимальный Create, все поддержанные поля записи, частичный Update,
  отсутствие незаданных полей, явные false, пустую строку и кодирование null.
  Проверка кодирования null не имитирует и не доказывает его принятие живым сервером.
- Проверить локальную валидацию, nil client/context, отмену context,
  APIError для 4xx/5xx, сохранение исходных ошибок и контекста операции.
- Проверить неожиданный статус, malformed JSON, null и ответ без ID;
  отсутствие автоматического повтора запроса.
- Проверку gzip и общих заголовков использовать по образцу Product,
  не создавая новый транспорт или новую общую тестовую инфраструктуру.
- После небольшого изменения запускать относящиеся к нему проверки.
  По завершении ticket выполнить форматирование, go test -race -count=1 ./...,
  go vet ./... ./testdata и git diff --check по действующим правилам проекта.
- Живой аккаунт не использовать в рамках этих проверок.

## Out of Scope

- Сущность Service: её планирование и конфликт имён отложены.
- List, поиск, фильтрация, сортировка, пагинация, Delete и массовые операции UOM.
- Expand, metadata, фасад SDK и универсальный механизм выполнения запросов для всех сущностей.
- Новые поля вне согласованного перечня, новые правила общих типов и переработка Product.
- Retry, 429, rate limiting и остальные универсальные доработки транспорта.
- Примеры с записью в живой аккаунт, чтение .env, push и публикация PR.

## Further Notes

- Контракт и проверки согласованы пользователем: «q1 q2 делаем по образцу Product».
- Имена UOM, Service и NewService сохраняем сейчас; возможное переименование
  рассматривается позже и не блокирует этот срез.
- Product принят пользователем как образец; зафиксированный в плане коммит — 9bca259.
- Официальная документация — основной контракт; upstream-фикстура не доказывает
  обязательность полей или допустимость их записи.
- [UOM: поля и операции](https://dev.moysklad.ru/doc/api/remap/1.2/#/dictionaries/uom).
- [Исходник опубликованной документации UOM](https://github.com/moysklad/api-remap-1.2-doc/blob/master/md/dictionaries/_uom.md).
- [Правила null](https://dev.moysklad.ru/doc/api/remap/1.2/#/general#3-podderzhka-null).
- Реализацию вести одним агентом, законченными файлами или смысловыми этапами,
  например полная модель чтения вместе с её тестами. Не дробить один файл по отдельным полям
  и не разделять red/green одного этапа на отдельные ответы.
- Объяснять назначение этапа и результат проверки. После завершённого этапа
  останавливаться для разбора пользователем; продолжать после его команды.
- Разбиение на tickets и их зависимости согласовываются отдельно перед сохранением.
  Статус этой spec означает готовность требований; он не разрешает реализовать весь срез одним заходом.
