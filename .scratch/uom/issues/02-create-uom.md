# 02: Создание пользовательской UOM

## What to build

Разработчик решения создаёт пользовательскую UOM через `uom.Service.Create`,
передавая обязательное имя и выбранные необязательные поля, и получает модель ответа сервера.

Контракт: [spec UOM](../spec.md). Утверждённый образец — Product.
Использовать модель UOM и обёртку из ticket 01, сохраняя общие типы и транспорт.

## Acceptance criteria

- [ ] CreateRequest содержит обязательный Name типа string; Description, Code
  и ExternalCode типа model.Field[string]; Owner и Group типа model.Field[model.Reference];
  Shared типа model.Field[bool]. Для Field используется omitzero.
- [ ] Meta, ID, AccountID и Updated отсутствуют в модели запроса.
- [ ] Create принимает context и CreateRequest, возвращает (*UOM, error)
  и выполняет POST на entity/uom с одним объектом запроса.
- [ ] Name=="" отклоняется до HTTP-запроса. Не добавлять trim,
  проверки длины и новые правила валидации по сравнению с Product.
- [ ] Минимальный запрос содержит только name. Полный запрос содержит все семь
  поддержанных полей записи; незаданные Field отсутствуют в JSON.
- [ ] Сериализация проверена через encoding/json и encoding/json/v2;
  явные false, пустая строка и null не теряются. Кодирование null
  не объявляется доказательством его допустимости для поля на сервере.
- [ ] Ожидаемые golden JSON заданы независимо от сериализации SDK
  и сравниваются по принятому в Product подходу.
- [ ] Локальный HTTP-тест проверяет метод, маршрут, тело, заголовки,
  декодирование обычного/gzip-ответа и значения возвращённой UOM.
- [ ] Возвращаются данные ответа сервера. Успех требует HTTP 200 и непустой ID;
  неожиданный статус, некорректный JSON, null и ответ без ID дают ошибку и nil.
- [ ] Проверены APIError для 4xx/5xx, исходная ошибка построения/выполнения запроса,
  nil context и отмена. errors.As/errors.Is и контекст операции сохранены,
  префикс moysklad: не дублируется.
- [ ] Предварительного Get и автоматических повторов POST нет.
  После неоднозначного сбоя SDK не создаёт повторную UOM автоматически.
- [ ] Документация поддержки дополнена Create UOM, его полями и ограничениями;
  Update не объявлен реализованным заранее.
- [ ] По завершении ticket пройдены форматирование, go test -race -count=1 ./...,
  go vet ./... ./testdata и git diff --check.

## Учебные шаги

Два законченных этапа: полная CreateRequest с проверками сериализации и golden;
затем публичный Create с HTTP-тестами успешного ответа, валидации и ошибок.
Внутри этапа выполнить red/green без остановки между ними и без дробления по полям.
Объяснять назначение этапа и результат проверки. После завершённого этапа
останавливаться для разбора и ждать команды пользователя.

## Границы

Не добавлять Update, массовое создание, фасад, retry и новые общие механизмы.
Не использовать живой аккаунт и .env. Реализация — один агент;
ревью и локальный commit выполняются после завершения всего ticket по правилам проекта.
Промежуточный незавершённый этап не коммитить. Новые решения контракта согласовывать.
