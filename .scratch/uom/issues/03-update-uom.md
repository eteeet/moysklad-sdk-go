# 03: Частичное обновление пользовательской UOM

## What to build

Разработчик решения изменяет выбранные поля пользовательской UOM через
`uom.Service.Update`, не отправляя остальные поля, и получает модель ответа сервера.
При попытке изменить предустановленную UOM он получает ошибку API.

Контракт: [spec UOM](../spec.md). Утверждённый образец — Product.
Использовать модель UOM и обёртку из ticket 01, сохраняя общие типы и транспорт.

## Acceptance criteria

- [ ] UpdateRequest содержит Name, Description, Code и ExternalCode типа model.Field[string];
  Owner и Group типа model.Field[model.Reference]; Shared типа model.Field[bool].
  Для всех полей используется omitzero.
- [ ] Meta, ID, AccountID и Updated отсутствуют в модели запроса.
- [ ] Update принимает context, ID и UpdateRequest, возвращает (*UOM, error)
  и выполняет PUT на entity/uom/{id}.
- [ ] Форма UUID проверяется по образцу Product, без ограничения версии.
  Неверный ID и UpdateRequest без заданных полей отклоняются до HTTP-запроса.
- [ ] Явные false, пустая строка и null считаются заданными полями;
  дополнительные ограничения значений проверяет сервер, как в Product.
- [ ] Отправляются только заданные поля. Нет предварительного Get,
  локального слияния и локального определения происхождения UOM.
- [ ] Сериализация проверена через encoding/json и encoding/json/v2;
  незаданные поля отсутствуют, явные false, пустая строка и null не теряются.
  Возможность передать null не обещает его принятие сервером.
- [ ] Независимые golden JSON закрепляют частичное обновление и поддержанные поля записи
  по принятому в Product подходу.
- [ ] Локальный HTTP-тест проверяет метод, маршрут, тело, заголовки,
  декодирование обычного/gzip-ответа и значения возвращённой UOM.
- [ ] Возвращаются данные ответа сервера. Успех требует HTTP 200 и непустой ID;
  неожиданный статус, некорректный JSON, null и ответ без ID дают ошибку и nil.
- [ ] Отказ сервера при изменении предустановленной UOM доступен как APIError.
  Локальный тест подтверждает передачу ошибки, а не поведение живого аккаунта.
- [ ] Проверены 4xx/5xx, исходная ошибка построения/выполнения запроса,
  nil context и отмена. errors.As/errors.Is и контекст операции сохранены,
  префикс moysklad: не дублируется. Автоматических повторов нет.
- [ ] Документация поддержки дополнена Update UOM и явно указывает,
  что предустановленные UOM изменять нельзя; остальные возможности остаются TODO.
- [ ] По завершении ticket пройдены форматирование, go test -race -count=1 ./...,
  go vet ./... ./testdata и git diff --check.

Create не является технической зависимостью Update: ответы предоставляет локальный
HTTP-сервер, создания данных в живом аккаунте не требуется.
Для учебного порядка пользователь выбрал выполнение 01 → 02 → 03.

## Учебные шаги

Два законченных этапа: полная UpdateRequest с проверками состояний Field и golden;
затем публичный Update с HTTP-тестами успешного ответа, валидации и ошибок.
Внутри этапа выполнить red/green без остановки между ними и без дробления по полям.
Объяснять назначение этапа и результат проверки. После завершённого этапа
останавливаться для разбора и ждать команды пользователя.

## Границы

Не добавлять Delete, массовые операции, фасад, retry и новые общие механизмы.
Не использовать живой аккаунт и .env. Реализация — один агент;
ревью и локальный commit выполняются после завершения всего ticket по правилам проекта.
Промежуточный незавершённый этап не коммитить. Новые решения контракта согласовывать.
