## Правила работы, обновлены 2026-10-31

- Реализация — один агент в отдельной сессии на согласованный ticket.
- Планирование четырёх справочников выполняется в текущей сессии; реализация — в новых.
- Внутри ticket нет учебных остановок по файлам или между red/green: агент выполняет согласованный объём целиком. Новые контракты по-прежнему требуют согласования.
- Субагенты разрешены для ревью: отдельные проверки Standards и Spec по стандартному code-review.
- Пользователь хочет попробовать стандартный implement: реализация, тесты, встроенное ревью, локальный коммит без отдельной команды на коммит каждого ticket. Это заменяет прежнее правило ожидать ручного одобрения перед таким коммитом.
- Reviewer сообщает замечания и не изменяет код. Исправления в пределах согласованного ticket делает основной implementer; новые решения контракта согласуются с пользователем.
- После ticket агент сообщает SHA коммита, результаты проверок, что проверить пользователю и предлагаемую следующую захватку; затем ждёт команды. Ручной контроль пользователя сохраняется после готового локального коммита.
- Push, публикация PR и действия на VPS требуют отдельной команды. Commit сохраняется только в локальном Git-репозитории; для ревью на VPS код нужно отдельно передать, например через push в GitHub и fetch на VPS.
- Работа с .env и живым API не входит в реализацию по умолчанию. Секреты в коммиты не включаются.
- Настройку skills и этот временный план не коммитить автоматически под видом реализации ticket.

Ссылки на tracker, triage и domain docs уже подключены через AGENTS.md.
Этот временный roadmap и правила передачи контекста пока нужно передавать новой сессии явно.

## Как масштабируем

Образцы — Product и завершённый UOM. Service намеренно пропущен и остаётся отложенным.
Дальше работаем по семействам: один согласованный представитель, затем похожие сущности законченными проверяемыми срезами.
Похожесть не означает одинаковый контракт или поддержку одинаковых методов.

Текущие копии приватных do и validID в пакетах сущностей допустимы.
Общую абстракцию и рефакторинг именования сейчас не вводим; возвращаемся к этому при реальной потребности.
Правило синхронизации общих исправлений и сохранения обоснованных различий записано
в [известных TODO покрытия](coverage.md#известные-todo).

Перед каждой сущностью сверить официальную документацию и образец Product. В чат на согласование вынести отличия:

- поддерживаемые методы и маршруты;
- поля чтения и записи, обязательность и доступность изменения;
- отсутствие поля, null, нулевые и пустые значения;
- новые вложенные структуры и ссылки;
- слияние или полная замена коллекций при обновлении;
- особенности чисел, дат, статусов ответа и ошибок.

Любой новый контракт, которого нет в утверждённом образце, сначала согласовать, затем реализовать.
Это относится и к отличиям внутри уже согласованного семейства.

## Pipeline skills

Разовая настройка выполнена: используется локальный Markdown tracker `.scratch/`,
правила tracker, triage и domain docs доступны через AGENTS.md.

Для нового семейства:

1. grill-with-docs: изучить документацию и код, представить отличия и варианты, согласовать контракт. До согласования — обсуждение, не реализация.
2. to-spec: записать согласованные требования, границы и критерии приёмки; согласовать точки проверки публичного поведения тестами.
3. to-tickets: предложить законченные проверяемые срезы и зависимости; сохранить после одобрения пользователем. Для текущей группы утверждены пять tickets: четыре сущности целиком и отдельный публичный JSON-контракт общих типов реквизитов.
4. implement: в новой сессии один агент выполняет один ticket через TDD, запускает проверки, встроенное ревью с субагентами, затем локально коммитит результат.
5. Пользователь проверяет результат; при необходимости отдельный агент на VPS выполняет дополнительное ревью после согласованной передачи кода. Исправления — последующие коммиты, затем повторная проверка.

Обсуждение → spec → tickets желательно провести в одной сессии, чтобы сохранить причины решений.
Для новой сессии реализации ticket должен быть самодостаточным: требования, критерии приёмки, зависимости и ссылки на нужные решения, а не ссылка «как договорились в чате».
После реализации агент останавливается; следующий ticket запускается отдельно.

При ревью явно задавать исходный BASE и spec/ticket. Если изменения ещё не закоммичены, учитывать рабочий diff и содержимое новых untracked-файлов: одно сравнение коммитов их не покажет.

### Тесты и границы расширения

- Официальная документация — основной контракт; OpenAPI и фикстуры могут отставать.
- Upstream-фикстуры использовать без изменений, сохраняя происхождение и зафиксированную версию по принятому в проекте механизму.
- Проверять значения значимых полей, а не только успешное декодирование JSON.
- Тела запросов проверять через независимо заданные golden-файлы; закреплять false, 0, пустые значения и null там, где они допустимы.
- Проверять HTTP-метод, путь, тело, декодирование ответа и ошибки; совместимость JSON-кодеков — по образцу существующих тестов.
- List/query/пагинация, positions и другие отсутствующие возможности сначала проходят собственный согласованный срез. Они не появляются автоматически при копировании сущностей.
- Expand отложен. Retry, 429, rate limiting, дополнительные заголовки и остальные универсальные доработки транспорта — отдельные захватки по мере необходимости. Delete и массовые операции в начальный Service не включать.

## Переход в новую сессию

После подготовки spec и tickets передать агенту:

```text
Прочитай AGENTS.md, CLAUDE.md, docs/temp_plan.md и настройку docs/agents/.
Прочитай спецификацию <путь> и ticket <путь>.
Выполни только этот согласованный ticket через implement.
Реализация — один агент; для ревью разрешены субагенты.
Локальный коммит разрешён по завершении ticket. Push — только по отдельной команде.
Внутри ticket не делай учебных остановок по файлам или между red/green.
Новые контракты сначала согласуй со мной. После результата остановись и жди.
```

Этот шаблон использовать после утверждения и сохранения tickets; заполнить пути.
Удалить временный файл после завершения соответствующих работ и переноса остающихся правил и плана в постоянные документы. Пока не удалять.
